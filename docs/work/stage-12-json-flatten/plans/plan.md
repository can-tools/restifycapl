# Stage 12 — JSON flattening (third append to the export table)

Slug: `stage-12-json-flatten`. Branch: `stage/12-json-flatten`, created from green `main`.

## 1. Goal

Add to the DLL a parsed JSON document stored on the DLL side and addressed by a handle number (`documentId`). The document is flattened to a list of key/value/type entries, where keys are JSON Pointer (RFC 6901), in document order. Added to this are reads by index and by path.

Expose this to CAPL as rows 19–25 of the `CAPL_DLL_INFO_LIST4` table, in the `Json` category.

In passing:
- replace the interim path syntax from Stage 8 with RFC 6901 syntax, which is now the contract;
- move in core to `ordered_json`;
- start the preliminary CAPL framework in `capl/` (D22): one include entry point, wrapper libraries, and verification nodes the user attaches in a CANoe configuration and verifies iteratively;
- local build environment (D23, user request): `scripts/setup-dev-env.ps1` stores each architecture's MSVC environment in user environment variables and the `Makefile` uses the set matching `ARCH` when present, so both architectures build from any new shell; bare `make` prints the target list;
- apostrophe-quoted JSON strings (D24, user request): JSON written in CAPL may use `'…'` instead of `\"…\"`; `restifyJsonParse` accepts it directly, and the new row 25 `restifyJsonNormalize` turns such text into standard JSON before it is sent as a request body.

`examples/` stays empty in this stage (D13). Stage 13 (typed accessors) will use the same document.

| D19 | review follow-up | New limit on the total flattened key text: `kMaxFlatKeyBytes = 4194304` (4 MiB), status `KeyTextTooLarge` (−36). Reason: each entry key repeats its full path, so a 1 MiB text within the depth and entry limits can otherwise produce gigabytes of key text, ending in `bad_alloc` → −35. Counted: the sum of the byte lengths of all entry keys exactly as `ReadEntry` returns them (after `~0`/`~1` escaping, without NULs; array index = its decimal digits; root key `""` = 0; an empty container counts its own key). Counted in the SAX pass, per occurrence in the text before duplicate collapse, so the count is an upper bound of the stored total (exact without duplicates); no second check in the flatten pass. Overflow-safe comparison (32-bit `size_t` on x86). Precedence: −32 before scanning; during scanning the first limit reached in the text decides; if one leaf exceeds both −34 and −36, −34 is reported. Only `restifyJsonParse` can return −36. Value justification: 4 × the input limit, ≈ 419 bytes average key at 10,000 entries (several times realistic paths); bounds key text to 32 MiB across all 8 slots. `FlattenJson` may still throw `std::bad_alloc` on genuine memory exhaustion; the text layer maps it to −35 (D15). |
| D20 | review follow-up | `FlattenJson` rejects any NUL byte inside its input text with `ParseError` (−10). Reason: the JSON lexer treats NUL as end of input, so `[1]<NUL>garbage` would otherwise be silently accepted as `[1]`, contradicting "trailing content is invalid JSON". Order: after the −32 size check and the empty-text check, before the apostrophe conversion (D24) and before scanning. Not observable through CAPL (the text layer already ends the text at the first NUL); it protects future internal callers that pass a text directly. |
| D21 | review follow-up | A NUL character in an object key (written `\u0000` in JSON) is rejected with `ParseError` (−10) in the SAX pass at the key event. It is checked in text order, so it competes with −33/−34/−36 by "first reached in the text". Reason: CAPL strings end at NUL, so such a key would show up truncated in `ReadEntry`, could not be addressed by path, and could silently alias another key (`{"a":1,"a\u0000b":2}`). A NUL inside a string **value** stays accepted: the value text is stored and copied with its full length, and CAPL sees only the part before the first NUL; documented only. |

| D24 | user request | **Apostrophe-quoted JSON strings.** Purpose: JSON written in CAPL source may use `'…'` for strings instead of `\"…\"`; both notations are equivalent. (1) **One shared conversion function** in `src/mapping/json-quotes.{h,cpp}` (pure logic, no CANoe, no store): `Status ConvertApostropheStrings(std::string_view in, std::string& out)`, a single left-to-right scan with three states. **Outside any string:** every byte is copied unchanged, except `'`, which starts an apostrophe string and is written as `"`; `"` starts a double-quoted string and is copied. **Inside a double-quoted string:** every byte is copied unchanged until the closing `"`; a `\` and the byte after it are copied as a pair without interpretation, so standard JSON escapes keep working and `\'` stays `\'` (not a JSON escape, so the parser then reports −10); an apostrophe inside a double-quoted string is an ordinary character (`"it's"` is valid). **Inside an apostrophe string:** `\'` becomes a literal `'`; every other `\x` pair is copied unchanged (so `\\` is a literal backslash, and `\n`, `\"`, `A` keep their JSON meaning); a raw `"` is written as `\"`; a raw `'` closes the string and is written as `"`; all other bytes are copied unchanged. An unterminated string at the end of the text is left as it is, and the parser reports −10. Nothing outside strings changes: numbers, whitespace, `true`/`false`/`null`, structure and the order and duplication of keys stay exactly as written; a text without any `'` outside double-quoted strings comes out byte-identical. The function never adds a NUL. - No name can be a strict prefix of another.
- Shim does not load a reference parameter into a local variable.

- Never return a raw text pointer.

**Layers:**
- `src/mapping/` may depend on `src/core/`, not vice versa.

## 9. Risks

CAPL assumptions in the framework.** Confirmed at the first CANoe compile: `#pragma library` and `#include` paths with the `.\` prefix resolve relative to the file that contains them (the `#pragma library` rule is also documented by Vector); `key` is a CAPL keyword and cannot be an identifier (it caused all six errors of the first compile; fixed in step 11f). Still to confirm in HUM-29 (deferred until a CANoe licence, R31): the `#if X64` selection; reference parameters in user-defined `.cin` functions; `elcount()` on an array parameter; quoting of a JSON text in a `char[]` initializer for the offline check; how the CAPL compiler treats `\\` and `\'` in string literals (form B of D24). The directory layout itself is user-verified. Further compile errors may surface once the first ones are fixed; the compile after the D24 changes is confirmed on x64 (5a32872). Mitigation: HUM-29 items (1), (3), (4), (6), (7); fallback for reference parameters (one-element array). A failure here does not touch the DLL or the export table.
- **R23. Name clashes** between framework functions and users' own CAPL functions or other DLLs loaded in the same configuration. Mitigation: `restLib` prefix and the `restify` → `restLib` naming rule, which keeps wrapper names prefix-free like the export names.
- **R24. Stale or mismatched DLL.** The user copies DLLs by hand, so a DLL from one commit can meet libraries from another: a newer library calling a row the DLL lacks fails loudly at compile time; the reverse is harmless because DLL rows are append-only. If a DLL is missing from `capl/includes/dll/…`, CANoe may pick a same-named copy from a `capl_includes` fallback folder. A DLL loaded by CANoe cannot be overwritten until CANoe releases it. A DLL could be force-added to Git. Mitigation: `docs/capl-framework.md` (same commit/tag, close CANoe before copying, no copies in `capl_includes`); both nodes print the DLL version at start; `*.dll` ignored and REV-7 item 19 checks `git ls-files "*.dll"`. Once others rely on the framework, renaming or removing a wrapper breaks their scripts like an export-table change, and scope creep toward deferred modules is possible through "small helpers". Mitigation: "preliminary" status until the user's decision (§7 item 17), the D22 boundary, and REV-7 item 19. Dependence on `https://httpbin.org` for HUM-30 is reduced by the offline JSON check and covered by the URL variables.
- **R25. Default goal change.** Bare `make` no longer builds; anything relying on it (habit, an external script) now gets the target list. GNU convention makes `all` the default goal; this project departs from it deliberately (D23). CI is unaffected because it always names its targets. Mitigation: help text names the build targets; `CLAUDE.md`/README/skill updated (HUM-32, step 14).
- **R26. Stale or invisible variables.** The stored values contain versioned Visual Studio / Windows SDK folders; after a Visual Studio / Build Tools update the old folders disappear and builds fail until `setup-dev-env.ps1` is re-run. Windows and VS Code opened before the setup run do not see the variables. If the setup runs elevated under a different administrator account, the variables land in that account's profile. Mitigation: README (re-run after update, open a new window / restart VS Code, run elevated as the own account via UAC); the setup summary reports the verified architecture of each stored set.
- **R27. `PATH` handling and precedence in the `Makefile`.** GNU make on Windows treats the `Path`/`PATH` spelling specially and may run simple commands without `cmd.exe`; the exported `PATH` must provably reach `cl.exe`/`link.exe`/`rc.exe`. When the variables exist they also take precedence inside an already activated MSVC shell (a deliberate consequence: `ARCH` decides). A wrong-architecture build is still possible only where the variables are absent and the shell targets the other architecture (`LNK1112`, as today). Mitigation: the step 11d real-run list (both spellings set if needed); CI keeps using its own environment because the variables are absent there.
- **R28. CI green while local x86 failed.** At 25f2f6f the x86 tests failed locally (3 of 571) while CI reported green; the cause is not established (failing commit not run to completion in CI, or a machine-dependent outcome of the dangling `setlocale` pointer). Tests that change global state (the C locale) can pass in CI unnoticed and break other tests elsewhere. Mitigation: fix in 569fc6a; step 14a (CI log review, cause, HUM-34 decision on the per-test locale check and on the `de-DE` test not skipping in CI).
- **R29. Apostrophe conversion (D24).** (a) A bug in the conversion could alter valid JSON; mitigation: apostrophe-free text must come out byte-identical (pinned by test) and the conversion is skipped when the text has no `'`. (b) `'it's'` is ambiguous and gives −10; mitigation: documented in `docs/`, README and the verification nodes, with forms A and B. (c) Form B depends on how the CAPL compiler treats `\\` and `\'`, which is not yet verified; if CAPL passes both backslashes, form B gives −10 (loud, not a silent change) and is documented as not usable from CAPL; mitigation: HUM-29 (7), deferred until a CANoe licence; until then README and docs mark form B as not yet verified. (d) `\'` inside a double-quoted string is not converted and gives −10, which may surprise; documented. (e) The normalized text can be longer than the input (added `\` before `"`), so the output buffer may need to be larger; −2 with retry, documented. (f) Row 25 checks JSON syntax only, not the depth/entry/key-text limits of row 19 — a normalized body may still be rejected by row 19 if parsed later; documented. (g) Request bodies are never changed silently: only an explicit call to row 25 converts them.
- **R30. x86 DLL never loaded by CANoe.** No 32-bit CANoe configuration is available, so the #if X64 else-branch, the x86 DLL load and x86 calling-convention correctness in CANoe (R10) stay unverified; x86 is covered only by the GoogleTest suite in CI. Mitigation: one parameterized build rule for both architectures, CI on both legs; gap stated in docs/capl-framework.md.
- **R31. No CANoe licence.** HUM-29 items (1), (3), (4), (6), (7) and HUM-30 need a running measurement and a CANoe licence the user does not have now. By user decision they do not block the merge (D14): Stage 12 merges with the x64 compile confirmed and runtime behavior in CANoe unverified, and Stage 13 starts afterwards on top of it. Consequence: a defect found later (e.g. reference parameters, elcount(), form B) is fixed after merge in a follow-up change; export rows are not affected (CAPL-side fixes or documentation only, unless a DLL defect is found). Mitigation: README and docs/capl-framework.md state what is not yet verified; GoogleTest coverage on both architectures in CI.
